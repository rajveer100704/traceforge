## 0. Executive assessment

TraceForge v0.2.0 already has substantial metric and benchmark infrastructure. Do **not** rebuild the evaluation layer from scratch.

Already implemented (verify against current checkout before changing):
- Wilson score intervals and task-clustered percentile bootstrap intervals.
- Independent-task and episode counts (`n_tasks`, `n_episodes`), per-task rows, per-seed breakdowns, split/family/difficulty breakdowns.
- Reward-threshold sensitivity at 0.1 / 0.25 / 0.5 / 0.75 / 0.9.
- Verified success, partial success, verifier errors, positive reward, false-positive reward, regression failures, hidden-security pass rate, mean reward and CI, tool calls, action rejection, duration, token totals, generation latency.
- Fail-closed benchmark integrity checks for split/task lineage and training overlap.
- Reproducibility bundles with code/config/data/model/checkpoint hashes, raw episode JSONL, metrics, environment, and reproduce commands.
- SFT assistant-only loss masking and LoRA path; GRPO adapter using TRL `environment_factory`; explicit CPU/CUDA and precision selection.
- OpenAI-compatible provider with usage extraction and optional per-1K token price inputs.
- Experiments A–H and explicit `NOT EXECUTED` state for real model arms.

The major outstanding work is **research execution and metric validity**, not a blank-slate metrics engine:
1. Execute a real baseline model, SFT, and (only after SFT works) GRPO on exactly comparable held-out tasks.
2. Make metric semantics complete and auditable (especially cost, latency, denominators, missing telemetry, paired comparisons).
3. Strengthen benchmark breadth and task independence; the current suite is synthetic, offline, 3 cybersecurity families × 3 templates with just 9 private task instances.
4. Establish model/task budgets, seeds, power/precision rationale and immutable official run protocol.
5. Test that learned policies genuinely improve held-out verified outcomes and do not just increase reward, token spend, or exploit the verifier.
6. Improve isolation before running untrusted model-generated code; local sandbox is trusted-demo-only; Docker is still not a hostile multi-tenant security boundary.

### Evidence boundary
v0.2 scripted `demo_provider` measurements validate infrastructure, not learned model ability. Existing F cpu-test uses a tiny random model and 4 optimiser steps; G model arms have no endpoint. Neither constitutes model training/evaluation evidence. Never call a scripted arm a model baseline or infer generalization from it.

- Historical verifier/task 1.0.0 preserved for re-verification.

## 1. Research questions and primary hypotheses

### RQ1 — Does curation level affect agent post-training?
Compare D1 raw, D2 schema-valid, D3 independently verified successes, D4 verified successes plus informative verified failures.
- **H1:** D3/D4 improve held-out verified task success over D1/D2 at a fixed training compute/data budget.
- **H2:** D4 can outperform D3 when informative failure trajectories add useful recovery behaviour, but may harm if failure examples are noisy or poorly formatted.
- **H3:** verified dataset levels reduce unsafe actions / false-positive reward compared with raw data.

### RQ2 — Does SFT improve the base model?
- **H1:** SFT improves private held-out task verified-success rate, not merely training loss or visible-test success.
- **H2:** gains survive family/template/difficulty breakdowns and are not concentrated in one family.
- **H3:** tool calls and tokens per verified success do not grow so much that efficiency-adjusted performance gets worse.

### RQ3 — Does GRPO add value beyond SFT?
- **H1:** SFT+GRPO outperforms SFT on the same private benchmark with the same inference settings and task budget.
- **H2:** GRPO does not increase false-positive reward, policy violations, regression failures, or verifier errors.
- **H3:** any improvement is robust across at least three seeds and task families.

### RQ4 — Does verifier/reward robustness generalize?
- **H1:** verifier 1.1.0 rejects known development attacks and the held-out attack set.
- **H2:** independently authored future attacks do not cause false-positive authoritative rewards.
- Do not claim ungameability. Report exact attack coverage and the number of held-out task clusters.

## 3. Phase 1 — Metric correctness and benchmark report completeness (P0)

**Do this before real model runs**, otherwise valuable GPU/API runs can produce incomplete evidence.

### 3.1 Define metric contracts and denominators

Create a machine-readable metric registry/document (e.g. `docs/metrics-contract.md`, with tests) defining numerator, denominator, unit, aggregation, missingness, and interpretation:

| Metric | Numerator / value | Denominator / unit | Primary level | Notes |
|---|---|---|---|---|
| Verified success rate | authoritative PASS | all eligible episodes | task-clustered + task-level | Report PARTIAL separately |
| Partial success rate | authoritative PARTIAL | all eligible episodes | task-clustered | Not counted as success |
| Verifier error rate | ERROR or INCONCLUSIVE | all eligible episodes | task-clustered | Keep infra/provider failures distinguishable |
| Hidden-security pass | hidden security PASS | episodes where check executed | task-clustered | Also report check coverage; missing ≠ pass |
| Regression failure | regression FAIL | episodes where check executed and all episodes | both | State both denominator and coverage |
| False-positive reward rate | undeserving episodes with reward ≥ threshold | episodes independently labelled undeserving | per attack + clustered task | Never use model's own self-report as ground truth |
| Reward precision | rewarded episodes that are truly successful | rewarded episodes with valid labels | attack/task clustered | Labelled-only metric |
| Reward recall / true-positive reward | truly successful episodes rewarded | truly successful labelled episodes | task-clustered | Distinct from verifier recall |
| Tool calls / verified success | total calls / PASS episodes | successful episodes | task-level distribution | Do not average per-run ratios blindly |
| Tokens / verified success | total prompt+completion tokens / PASS episodes | successful episodes | per-task + aggregate | Report prompt/completion separately |
| Cost / verified success | actual provider USD / PASS episodes | successful episodes | per-task + aggregate | Unknown pricing must be null, never silently $0 |
| Generation latency | per-request and per-episode wall time | requests/episodes | median, p90, p95, max + task summary | Include retries and timeouts explicitly |
| End-to-end latency | episode wall time | episodes | median, p90, p95, max | Separate model generation vs tool/verifier time |
| Tool efficiency | verified successes / tool calls, or calls per success | episodes / successful episodes | aggregate + per task | Pick one canonical direction |
| Policy violation rate | rejected/unsafe tool actions | tool actions and episodes | both | expose denominator |
| Training cost | wall seconds, GPU-hours, peak VRAM, tokens/examples | training run | each seed | record price estimate separately |
| Dataset quality | validated, quarantined, verified rows per D1-D4 | each curation level | dataset | row count and task coverage |

### 3.2 Fix concrete metric gaps identified in code review
Inspect and test `src/traceforge/modules/evaluation/metrics.py`, provider metadata plumbing and `src/traceforge/modules/evaluation/reports.py`.

1. `cost_per_verified_success_usd` currently returns `None` unconditionally. Implement only when all required price/cost fields are known; use provider-reported `cost_usd` as authoritative if recorded, else calculate prompt/completion tokens × configured rates. Null and include `cost_coverage` when pricing unavailable. Never coerce absent usage/pricing to zero.
2. Confirm OpenAI-compatible provider pricing configuration reaches every rollout summary. Provider has `price_per_1k_prompt` / `price_per_1k_completion`; inspect factory/config/contracts and persist cost/usage into summary metadata.
3. Latency: preserve each generation request's duration, retry count, timeout, model `finish_reason`; episode duration must include full run. Report p50/p90/p95 and max, not only mean. Do not lose latency when metadata is absent.
4. Telemetry coverage: add counts and fractions for episodes with known token usage, cost, generation latency, and each hidden check. Missing telemetry must be explicit; report `not_reported`, not zero.
5. Report failed and timed-out provider calls separately from verifier ERROR/INCONCLUSIVE.
6. Add `verified_successes_per_1000_tokens` only as a secondary efficiency measure, with prompt/completion split.
7. Add `cost_per_attempt`, `cost_per_success`, `tokens_per_attempt`, `tokens_per_success`, and `tool_calls_per_attempt/success` with explicit denominator and null handling.
8. Validate all output values are finite and serialize JSON-safe `null` for unavailable measurements.
9. Ensure report Markdown includes metric units, confidence/interval method, n tasks, n episodes, n labelled episodes, and missing telemetry count.
10. Ensure `summarize` does not count unavailable/`SKIPPED` hidden checks in the denominator; separately report check coverage.
11. `summarize` currently uses authoritative PASS fallback as ground truth when no label callback is given. For model benchmark, this is okay as a *verifier-derived verified success* metric, but false-positive reward rate is not independently measured without labelled adversarial episodes. Report that limitation; do not call it an independently labelled FP metric.
12. `n_seeds` should not be treated as independent n. Explicitly state the statistical unit for each measure.

### 3.3 Add paired model comparisons
Current per-arm marginal CIs are insufficient for claims that model B beats model A. Implement a paired task-level comparison report:
- Same task IDs, same task versions, same seed list, same benchmark protocol, temperature, token limit, sandbox, verifier/reward policy.
- For each task × seed compute paired difference in success (and secondary metrics).
- Aggregate at the independent task level. Use a task-cluster bootstrap of paired task differences; do not resample each episode independently.
- Report absolute percentage-point difference, relative difference (if meaningful), 95% CI, number of task clusters, and per-family differences.
- If task coverage does not match, refuse official paired comparison; allow only an explicitly non-official diagnostic report.
- Avoid p-values and "statistically significant" language unless the design and sample support it. CIs are more informative here.

### 3.4 Statistical quality
Current task-cluster bootstrap is sensible but tiny n (9 private tasks) makes intervals coarse/unstable.
- Expand task instances / families before treating results as strong population claims.
- Use a fixed, recorded bootstrap seed and >=10,000 resamples in final reports (2,000 may remain for development).
- Validate bootstrap coverage/sanity with simulation tests and edge cases (0%, 100%, one task, unequal cluster sizes, missing check).
- Consider BCa or hierarchical bootstrap as an explicitly versioned alternative only after implementation and validation; don't silently change historical v0.2 metric method.
- Add a separate paired cluster bootstrap.
- Report task-level scatter/distribution and not only pooled ratios.
- Do not use 3 random seeds as if they were 3 independent tasks.

### Phase 1 acceptance
- Metric contract covers all report fields.
- Unit tests cover absent provider usage, partially known price, 429 retries, timeout, failed episode, zero verified successes, zero tool actions, skipped checks, mixed task repetitions.
- Cost is computed from actual provider usage/prices or explicitly unavailable.
- p50/p90/p95 latency and telemetry coverage visible in JSON and Markdown.
- Paired comparison verifies identical task/seed coverage.
- Existing v0.2 bundles and historical outputs remain byte-for-byte unchanged.

## 4. Phase 2 — Improve benchmark design and task diversity (P0/P1)

The current task set is a useful controlled proof-of-concept, not a broad agent benchmark:
- 3 synthetic cybersecurity families: SQL injection, access control, SSRF.
- 3 templates per family; only one template/family private-held-out.
- 9 private tasks at present.
- Synthetic offline environments and local Docker harness; no real external systems.

### 4.1 Expand instances before adding many unrelated features
Create more independently generated task instances per task template and add templates only when oracle/test independence is real.
- Target for the first credible pilot: at least 30–50 independent task instances in private evaluation across 3+ families, with multiple structurally distinct templates per family.
- Stretch: 100+ independent tasks across 5–8 families for stronger claims.
- Treat these as planning targets, not formal power guarantees. Calculate power / precision after estimating task-level variance from pilot data.
- Ensure same-task seeds are repeated episodes, not independent task clusters.

### 4.2 Avoid trivial random variants
Current seeded instances vary values and fixture details; that creates instance diversity but does not by itself establish structural generalization.
- Add genuinely different templates / root causes / remediation paths.
- Keep train/validation/public/private holdouts by template and family where feasible.
- Add a new family only when its hidden verifier, functional regressions, safety oracle and reference solution have independent tests.
- Candidate synthetic offline families: path traversal/file access control, command injection remediation in a mock executor, insecure deserialization, authentication/session validation, unsafe archive extraction. Do not use live targets or real networks.
- Avoid adding SSRF subtasks that just restate existing SSRF cases.
- Add difficulty levels with clear operational definition and expert review.
- Include both positive controls (valid remediation) and negative controls (no-op, superficial patch, regression-inducing patch, unsafe patch).
- Keep oracle/hidden tests outside the agent-visible prompt and dataset.
- Ensure hidden tests are not imported in training, prompt context, logs or tool schema.

### 4.3 Split policy v2
- Split by template and task-family lineage, never random episode.
- Hold out at least one entire template per family for private test; ideally reserve one entire family for secondary out-of-domain test once enough families exist.
- Generate fixture hashes from canonical environment contents and oracle version; verify no duplicates across splits.
- Keep public test for iteration; private test only for scheduled official runs.
- Add content-level training contamination checks for re-imported fixtures under different task IDs, with normalized content fingerprints and near-duplicate detection.
- Treat contaminated/unknown provenance rows as blocked from official training.
- Version split policy and benchmark task catalogue; all prior reports retain their original version.

### 4.4 Benchmark curation and governance
- Maintain a separate benchmark owner/reviewer for private task authoring where possible.
- Add `attack_catalog` rule: attacks used to patch verifier become development attacks for that verifier version.
- Sealed test release/access process: checksum/encryption/access controls, never embed secrets or true private oracle content in public artifacts.
- Add task acceptance review checklist: spec ambiguity, oracle independence, reference patch, negative controls, difficulty, runtime budget, flaky rate, leakage audit.
- Run task reproducibility checks with repeated execution and seeds.

### Phase 2 acceptance
- New task families/templates have independent hidden/functional tests and clean lineage.
- Official benchmark private split contains at least 30 independent tasks for pilot.
- Content-level leakage audit runs before official training/eval.
- Catalogue and split versions hash into every bundle.
- No task-generation output or hidden oracle leaks into model-facing prompts.

## 5. Phase 3 — Real SFT baseline and Experiment F (P0)

### 5.1 Hardware and model choice
Do not start by assuming a local GPU is available. First run `traceforge doctor`, `nvidia-smi`, inspect VRAM, disk and network. Choose model based on accessible VRAM and task/tool-call format:
- Use a small, instruction-tuned, tool-capable causal LM that fits the actual hardware.
- Pin exact HF commit revision for model and tokenizer; prefer safetensors.
- Record license, model card, parameter count, context limit, quantization, tokenizer revision and hardware.
- If no GPU available, use a rented/hosted GPU or a supported inference/training service; compare total cost and data handling before uploading any private datasets.
- Never pretend cpu-test is real model evidence.
- Keep all tasks synthetic/offline; never send secrets, real exploit payloads, or private oracle files to external providers.

### 5.2 Establish baseline before training
- Serve the pinned base model via vLLM or compatible endpoint; ensure tool calling format and OpenAI-compatible interface work.
- Run one smoke task on public/validation split using Docker sandbox.
- Validate provider emits usage fields, request timing, model id/revision, finish reason, retries, cost.
- Then run official baseline on identical evaluation task IDs with 3–5 seeds and full budget; include validation/public and private evaluation only once configuration is frozen.
- Run at least two identical baseline repeats to estimate infrastructure/provider nondeterminism.
- Keep inference parameters frozen across arms: temperature, top_p if supported, max tokens, tool iteration budget, stop settings, concurrency.

### 5.3 Build four datasets
From the same verified corpus:
- D1 raw traces.
- D2 schema-valid traces.
- D3 verified successes.
- D4 verified successes + informative verified failures.
For each dataset report:
- raw / retained / rejected / quarantined / duplicate counts.
- verified success/partial/failure distribution.
- per-task and per-family coverage.
- assistant-token count, total token count, sequence length distribution and truncation/drop counts.
- unique trajectories, near-duplicate rate, contamination and lineage.
- train/validation counts; label balance; source policy and dataset manifest hashes.

### 5.4 Controlled F design
- Fixed base-model and tokenizer revision, LoRA architecture, optimiser, learning rate, sequence length, batch size, epochs/steps, scheduler, precision, GPU type, training-token budget and seed list.
- Only data curation level varies. If D1/D2 have more tokens, equalize training budget by tokens/steps and report row counts as a secondary difference; pre-register which estimand is being studied.
- Train D1–D4 for at least 3 seeds (prefer 5 when budget allows).
- Do not match `control_hash` only on config values if actual optimizer steps/tokens differ; store effective tokens trained, examples processed, optimizer steps and wall time.
- Validation set is allowed for model selection; private test is never used for early stopping, hyperparameter choice or checkpoints.
- Serve each arm checkpoint under unique immutable model IDs/endpoints; record adapter/checkpoint hash.
- Run each arm on exactly the same private task IDs and seed list.
- Primary outcome: task-level authoritative verified success rate; compare each D arm with D1 using paired task bootstrap.
- Secondary: hidden security pass, regression fail, verifier error, false-positive reward only where independent labels, tokens/cost/tool calls per success, latency percentiles, per-family/difficulty.

### Phase 3 acceptance
- Baseline model has measured results and valid usage metadata.
- F includes completed real training and evaluation arms (no `NOT EXECUTED` for primary arms).
- All training runs record dataset IDs/hashes, model/tokenizer revisions, checkpoint SHA, training task IDs, hardware, optimizer steps/tokens, and training budget.
- Paired model comparisons have matched tasks/seeds.
- No private split touched during training or model selection.
- If only some arms can be afforded, label pilot/incomplete; do not claim curation effect across all four.

## 6. Phase 4 — Real SFT vs GRPO Experiment G (P1, after SFT works)

### 6.1 GRPO readiness gate
Before long run:
1. Confirm installed `transformers`/`trl` versions support TraceForge's required `GRPOTrainer(environment_factory=...)` API.
2. Confirm GRPO environment adapter contract and reward type with a deterministic short integration run.
3. Run with Docker sandbox only for untrusted model output.
4. Confirm task prompts are train split only and official leakage guard sees all dataset and training lineage.
5. Record generated rollout raw episodes and authoritative verification evidence.
6. Set conservative `max_steps`, `num_generations`, max completion length, tool iterations and timeouts; estimate worst-case compute and spend.
7. Require GRPO reward to be derived exclusively from full authoritative verifier evidence; no self-reported reward shaping.

### 6.2 Arms
- Base model.
- SFT checkpoint from fixed dataset (choose pre-registered primary D level, probably D3 or D4 based on F; don't choose after private results).
- SFT + GRPO from exactly that SFT checkpoint.
- Optional: SFT on chosen D4 + GRPO; only if compute allows, clearly marked secondary.
- Same model family/revision, tokenizer, benchmark environment and evaluation generation settings.
- At least 3 training seeds; training seeds are paired to base checkpoint and data split.
- Model revision and checkpoint hashes immutable.

### 6.3 GRPO training telemetry
Record:
- total training wall time and GPU-hours.
- peak GPU memory and utilization if accessible.
- total prompt/completion tokens, generated trajectories, valid/invalid tool calls.
- reward mean/variance and component breakdown over time.
- verifier PASS/PARTIAL/FAIL/ERROR counts.
- policy violations and false-positive reward audit.
- KL if supported, entropy, clip fraction, grad norm, learning rate, loss.
- number of rollouts per task and task coverage.
- failed/aborted training steps and recovery/resume state.

### 6.4 Evaluation
Run all arms on identical official test tasks, seeds, inference config.
Primary: base→SFT and SFT→SFT+GRPO paired change in authoritative verified success.
Guardrails: hidden security pass, regression fail, verifier error, false-positive reward, policy violation, resource budget.
Efficiency: cost per verified success, tokens per success, tool calls per success, p50/p95 latency.
Stratify by family, template, difficulty, private/public split.

### Phase 4 acceptance
- GRPO adds or fails to add measurable held-out value. Either result is useful.
- No reward hacking or regression guardrail degradation hidden by mean reward.
- Full raw episode and training trace artifacts in bundles.
- Model deltas compared with paired task bootstrap.
- Report includes uncertainty and limitations, no unsupported significance claims.

## 7. Phase 5 — Verifier red-team and security robustness (P1, parallel track)

1. Keep v1.1 known/development and held-out catalogues distinct.
2. Author new verifier-v1.1 held-out attacks independently after v1.1 is frozen; store design rationale and hashes separately from verifier code.
3. Include multiple attack categories: output type/equality semantics, exception masking, evidence forgery, visible-test tampering, state mutation, tool-router boundary, path manipulation, time/resource exhaustion, grader confusion, tool result spoofing.
4. Attack the full stack (provider → router → sandbox → test executor → evidence store → reward), not only hidden assertion helpers.
5. Add trusted positive controls and negative controls.
6. Use fresh task fixtures and at least multiple independent templates/families per attack.
7. Test that a verifier change in response to any attack reclassifies it as development for that verifier version.
8. Report per-attack `n_tasks`, `n_episodes`, FP reward, TP reward, exact affected tasks, rejection reason and confidence intervals.
9. Add fuzz/property-based inputs for parsers, task oracles and evidence integrity.
10. Don't interpret 0 FP on a small test set as zero true risk; report upper CI bound and test scope.

## 8. Phase 6 — Sandbox and operational hardening (P0 before untrusted GPU/hosted model)

### Current boundary
- Local process sandbox is trusted demo only.
- Docker provider disables network and capabilities, uses read-only rootfs/non-root/resource limits, but Docker alone is not a hostile multi-tenant isolation boundary.
- Existing vulnerability documentation reports 11 HIGH CVEs with time-bounded exceptions through 2026-12-09; two SQLite FTS5 CVEs are noted as reachable from sandbox candidate code (contained by container but still a risk).
- In-process hidden-test execution has a residual tampering surface.

### Must-do
1. Triage CVE exceptions before 2026-12-09 or earlier when fixes appear; rerun Trivy on both images.
2. Add SQLite authorizer denying virtual tables/FTS5 in SQL tasks, unless those features are required (they are not); test bypass attempts.
3. Run hidden tests in a separate process/container with pristine test/oracle materials inaccessible to candidate process.
4. Consider gVisor/Kata/Firecracker microVM or equivalent stronger boundary for hostile multi-tenant execution; document threat model and limitations.
5. Restrict provider egress; redact secrets; model only receives synthetic specs and allowed tools.
6. Add resource quotas for CPU, memory, disk, processes, file descriptors, wall clock, network (deny) and generated output sizes.
7. Audit all artifact/prompt/log boundaries; hidden oracles and API keys must never enter prompts or public bundles.
8. Run security integration tests on the exact sandbox image digest used by experiments.
